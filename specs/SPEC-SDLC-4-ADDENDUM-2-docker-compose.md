## Why
The owner wants the e-store to run locally with a single `docker compose up`, so a friend can try it
with zero Ruby/Node setup. Docker **is** available in the authoring sandbox, so — unlike the rest of
this Rails example, which is correct-but-not-executed here — the Docker path can and MUST be **actually
built and run and verified**. That turns "it should work" into "it was run; here's the real output."

## The gap to close
`rails-estore/` is currently a teaching *subset*: it has models/controllers/views/specs and some
config, but it is **not a bootable Rails app** — it is missing the standard boot scaffolding. To make
`docker compose up` genuinely serve the app, complete it into a real, minimal, bootable Rails 8.1 app.

## What to add
### 1. Complete the Rails boot scaffolding (minimal, correct for Rails 8.1)
`config/application.rb`, `config/boot.rb`, `config/environment.rb`, `config/environments/{development,
production,test}.rb`, `config/puma.rb`, `config.ru`, `bin/rails`, `bin/setup`, `bin/rails`-executable
bits, and any initializers required to boot (e.g. `config/initializers/` defaults). Keep it minimal:
only what a small app with importmap/propshaft (no Node build needed) and SQLite requires. A
`Gemfile.lock` is generated by `bundle install` inside the build — do not hand-author it.

### 2. Docker files
- `Dockerfile` — based on the official Ruby image matching the pinned Ruby (verify the exact tag exists
  on Docker Hub, e.g. `ruby:4.0.6-slim`); install build deps for native gems (build-essential, and
  libsqlite3 for sqlite3), `bundle install`, copy the app, expose 3000. A dev-friendly image is fine.
- `docker-compose.yml` — a `web` service that builds the image, maps `3000:3000`, mounts the app for
  live edits, persists the SQLite database on a named volume, loads env from `.env`, and runs the app
  bound to `0.0.0.0`. **SQLite** keeps it single-service and "easygoing" (consistent with the existing
  DB choice); optionally include a **commented** Postgres service + note for those who want it. Do NOT
  hardcode any secret; env comes from `.env` (which is gitignored; `.env.example` documents it).
- `.dockerignore` (exclude `.git`, `tmp`, `log`, `node_modules`, local `.env`, the SQLite files).
- `bin/docker-entrypoint` — prepare the DB on boot (`./bin/rails db:prepare`) then exec the server;
  seed sample products so the catalog isn't empty on first run.

### 3. Actually verify it (Docker is available — this is required, not optional)
- `docker compose build` succeeds.
- `docker compose up` boots and serves: `curl -sf localhost:3000/up` (Rails health check) returns 200;
  the catalog (`/products` or root) renders; the login page renders. Capture the real output.
- `docker compose run --rm web bundle exec rspec` runs the suite in the container (report real
  pass/fail; fix what the run surfaces). Iterate build → run → fix until it genuinely works.
- Tear down cleanly. Do NOT leave containers/volumes/images running; do NOT commit any build artefact,
  `Gemfile.lock` churn aside (a committed `Gemfile.lock` from the real resolve is desirable — include it).

### 4. Docs
- `code/rails-estore/README.md` — add a **"Quickest start — Docker Compose"** section at the very top
  of the run instructions (`docker compose up`, then open `http://localhost:3000`), as the easiest
  path; keep the native macOS path as the alternative. State what actually ran/was verified.
- A short pointer in the chapter (`03-rails-estore-sdlc.md`) that the app ships a verified
  docker-compose setup for one-command local runs.
